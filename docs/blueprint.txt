PROJECT DEFINITION


01 Executive summary
Build an open-source short-video social platform with a familiar vertical feed, community-operated hosting, and a
purpose-built blockchain that coordinates hosting commitments. The objective is to remove a single mandatory
infrastructure owner, not to eliminate servers, bandwidth, operating costs, or accountability.

The final product has three parts: a viewer/creator application; software and a dashboard for independent
network operators; and an open protocol with its own blockchain. Normal viewers do not need to buy
cryptocurrency, approve blockchain transactions, or store other people's videos.

Recommended first release
Start with a responsive web app, moderated public videos, a small permissioned validator network, designated
storage hosts, and ordinary HTTPS video delivery. Keep the source and deployment specifications open. Add
optional peer-assisted delivery, alternative discovery services, and native mobile clients after the complete
upload-to-playback path works.

Why create a blockchain?
The proposed chain provides a common record of provider registrations, storage obligations, accepted evidence
and governance actions across independent operators. It is justified only if those operators need shared rules
without trusting one database administrator. Cosmos SDK supports application-specific logic; CometBFT supplies
the consensus engine. [S01, S05]

The project is not a new consensus algorithm, a video-inside-every-block system, or a token sale. Storage and
network capacity remain separate resources. Content addressing alone does not keep a file online. [S12]

  Decision                            Baseline

  Product                             Short-video app, operator software, public protocol specification.

  Blockchain                          Independent Go application chain; SDK modules and CometBFT.

  Network launch                      Known validators and providers; honest disclosure of operator control.

  Economics                           Quotas and explicit sponsorship; no tradable token in the beta.

  Success test                        A second operator can run the software; playback survives loss of one host.



   This document is a proposed implementation blueprint, not a deployed system or an audited protocol.
   Performance, total cost, user demand and production security have not been established.

PRODUCT DESIGN


02 Final products and user experience
The social application
The Home screen offers a chronological Following feed and a separate recommendation feed. Discover searches
public creators, topics and videos. Create supports uploads, basic trimming, captions and publication status.
Activity contains replies and notifications. Profile includes videos, account recovery, exports, privacy and
hosting-status controls.

A creator sees Uploading, Processing, Review pending, Replicating and Published as distinct stages. Published
means the app's moderation and hosting conditions are satisfied, not that a blockchain has certified the content as
lawful or truthful. Availability degraded and Hosting renewal needed must be visible states.

The operator product
An installation wizard lets an operator choose storage/delivery, processing, account/discovery, or validator roles.
The dashboard shows disk allocation, leases, job status, bandwidth, software updates, reports and service health.
Capacity limits and an orderly leave-network workflow are required. A storage operator need not become a
validator.

The developer product
Publish source code, versioned interfaces, schema files, test vectors, example clients and reproducible deployment
manifests. Compatible clients should be able to choose independently operated services. The project does not
become interoperable with ActivityPub, AT Protocol, IPFS or Filecoin merely by using similar concepts; each
integration needs its own adapter and tests. [S14, S19]

  User                                Acceptance outcome

  Viewer                              Watch, follow, block and report without a wallet or compulsory peer sharing.

  Creator                             Upload, understand status, recover an account, export records and request removal.

  Community operator                  Install independently, set local rules and quotas, process appeals and hand off hosting.

  Infrastructure operator             Accept bounded commitments, verify work, monitor costs and rotate service keys.

  Developer                           Build a second client against documented interfaces and a conformance suite.



   Long-term vision: a normal social-video experience on top of a network that can outlive the original
   deployment. That outcome must be demonstrated by independent operation, not inferred from a node
   count.

Proposed beta policy values
Limit uploads to 60 seconds and 100 MB of input per video, with one account allowance defined by its
community. Start with 480p and 720p portrait-friendly outputs, do not upscale smaller inputs, and keep a
separate cap on total output bytes. These are proposed constraints, not claims about maximum system capacity.

Use three operator-distinct copies of the accepted media package for publication, plus a separately managed
creator/origin backup policy. Three copies are a beta test parameter, not a durability guarantee. Count failure
domains as well as node identities.

Accessibility and safety requirements
Provide readable captions, accessible controls, keyboard navigation, reduced-motion settings, mute controls, and
predictable playback. Include reporting, blocking and community contact information from the start. Apple and
Google have user-generated-content requirements for apps distributed through their stores. [S22, S23]

Explicit non-goals
Do not build a proprietary-code clone, put personal viewing histories on a public ledger, promise universal
deletion, create a financial asset to fund an unmeasured system, or make every viewer a consensus participant. No
native-app launch is necessary to establish the first engineering result.

ARCHITECTURE


04 System architecture
Separate consensus, social records and media transport. The blockchain is the coordination layer. Account hosts
and indexes provide the social layer. Storage and processing nodes provide the media layer. Each has independent
authentication, failure handling and operational limits.


                                                          Viewer / creator client
                                                        No compulsory wallet or hosting




                Account + discovery services                                                          Media services

             Login, feeds, moderation, signed records                                         Processing, storage, HTTPS delivery


                                              Coordination records only; video bytes stay off-chain



                                                  Custom blockchain + validators

                                             Providers, commitments, evidence, governance




Trust and ownership boundaries
A community controls admission, its account service and its moderation decisions. A provider controls its machine
and the obligations it accepts. Validators order valid transactions; they do not automatically own videos or decide
every community's editorial rules. The initial council controls the permissioned validator set and protocol
parameters.

No mandatory commercial cloud
Provide a reference deployment on operator-owned or independently rented Linux machines. Optional
commercial services may simplify deployments, but DNS, identity, media storage, search and transaction access
must have documented replacement paths. A single mandatory gateway would remain a practical point of control.

The first beta can use signed provider manifests and HTTPS replication rather than public IPFS. Evaluate an IPFS
adapter later only after privacy, removal and operational behaviour are tested. PeerTube demonstrates an existing
HTTP/HLS plus optional WebRTC pattern; this project does not inherit its implementation automatically. [S14]


   A chain outage should pause new final commitments, not force every existing video to disappear. Hosts
   may serve already approved content under their last valid policy until the applicable real-time hosting
   deadline; the client must disclose stale status.

BLOCKCHAIN CREATION


06 Blockchain design and consensus
Create a new application chain with its own chain ID, genesis state, validator set, modules and upgrade policy.
Reuse the SDK's application framework and CometBFT's consensus rather than writing consensus from scratch.
No EVM, general-purpose smart-contract runtime, bridge or IBC connection is required for the first release. [S01,
S05]


Permissioned first, with explicit control
Use four equal-voting-power validators for the devnet. In the community beta, seek four genuinely independent
operators; until then, describe actual control accurately. Consensus safety requires the relevant Byzantine-fault
and network assumptions. With four equal validators, three form a greater-than-two-thirds quorum; one faulty
validator is below one third, while two unavailable validators prevent new commits. [S05, S06]

Implement x/authority as the sole source of authorized validator membership and scheduled power changes. Do
not simultaneously let a staking module overwrite the validator set. Validator updates must follow the selected
CometBFT/SDK lifecycle and activation semantics; test this explicitly. [S06]

Resource control without a tradable token
For beta chain writes, accept only approved operator and service accounts. Require signatures, account
sequences, explicit message authorization, bounded transaction size, execution gas metering and deterministic
write quotas. Zero monetary fees do not mean unlimited computation. The custom admission/ante path must
enforce the same consensus-critical rules during execution, not only in each node's mempool.

Viewers authenticate with the application. A service submits a creator's authorized hosting intent; providers sign
their own acceptance. A transaction broadcaster is not an IBC relayer. It must not be able to manufacture provider
acceptance or bypass a user's publication permissions.

Public-network gate
Permissionless validator or provider admission needs a separate Sybil-resistance and economic-security design,
audited incentives, dispute rules and operational diversity. Increasing the number of anonymous identities is not
sufficient. Do not describe the permissioned beta as trustless or permissionless.


   Proposed launch policy: no token sale, no exchange listing, no mining and no automatic financial slashing.
   The first chain records bounded obligations and evidence, not speculative returns.

Data that must stay off-chain
Video bytes, usernames tied to private details, email addresses, recovery secrets, individual watch events,
complaint narratives, private messages and legal evidence belong outside the public ledger. Store endpoint details
in signed off-chain manifests where possible. An opaque identifier or hash can still be linkable; hashing does not
automatically anonymize personal data. [S13, S24]

Suggested primary keys and indexes
Use stable IDs for providers, content, leases, proposals and evidence batches. Maintain indexes for
content-to-active-leases, provider-to-commitments, and deadlines-to-expiring-leases. Cap work per block and
paginate all queries; do not sweep the entire catalogue in every block.

Separate content from its current hosting
A media manifest is immutable for a given content version. Hosting locations, terms and publication status are
mutable records. A changed encoding produces a new package/manifest version; renewal of a lease must not
silently change the bytes previously committed.

08 Transactions, execution and invariants
Every state-changing message needs a named signer, authorization rule, replay protection, input bounds and
deterministic state transition. Treat all transaction data as hostile. Chain execution must produce the same state
from the same committed inputs. [S07]

  RegisterContent                     Approved host; user intent accepted by that host; valid   Create pending record; no
                                      digest; byte limit; unused content version.               hosting claim yet.

                                      terms; unexpired offer; declared capacity bound.          active obligation.

  SubmitAuditBatch                    Allowed auditor; valid signature; correct epoch;          Record attestation, not an
                                      accepted schema; unused evidence ID.                      unqualified storage proof.

  Renew / EndLease                    Authorized party; valid state; monotonic term version;    Extend agreed obligation or close

  Governance action                   Unique approvals; threshold; expiry; delay; valid         Schedule and execute an

Mandatory invariants
A provider cannot accept the same content version twice to count as two replicas. Declared reserved bytes
cannot exceed its declared admitted capacity. Lease and governance transitions cannot be replayed. Byte
counters cannot underflow or overflow. Expired evidence cannot renew current status. Withdrawal stops new
sponsored leases. These checks constrain accounting; they do not establish that physical capacity or operator
independence is truthful.

Deterministic execution discipline
Do not fetch videos, call an external API, run FFmpeg, read local wall-clock time, use floating-point scoring, or
iterate an unordered map to construct consensus state. Use committed chain context, integers, explicit sorting
and bounded work. External observations arrive as signed transaction inputs whose meaning is specified. [S07]

Commit acknowledgement
A successful broadcast or mempool response is not a committed successful transaction. The broadcaster waits for
inclusion and execution success, then updates the application projection. Persist the transaction hash, message ID
and result; reconcile after timeouts before retrying the business action.

Use an official example application to learn the scaffold, then remove unused functionality deliberately. The
reference quickstart includes modules that are not part of this proposal; a tutorial chain is not the final

  Step                                Concrete output

  1. Pin the stack                    Choose an active compatible SDK/CometBFT family; record exact commits, Go toolchain,
                                      licences and container digests.

  2. Create chain application         Create the Go module, app wiring, binary name, address configuration, API routes and test
                                      scaffolding.

  3. Define protocol types            Write tx.proto, query.proto, state.proto and genesis.proto for each custom module;
                                      generate code and review changes.

  4. Implement state                  Write keepers, authorization, message/query handlers, genesis validation, events,
                                      migrations and tests.

  6. Create genesis                   Generate public parameters and initial authorities; include no private keys or shared test

Genesis fields to specify
Define chain_id (example: shortvideo-dev-1), genesis timestamp, validator consensus public keys and voting
powers, application account addresses, council keys and threshold, admitted service/provider accounts, empty
content and lease state, resource limits and protocol versions. The final JSON schema depends on the selected
application and SDK; this is a required field inventory, not a ready-made genesis file.

Keys and network material
Generate validator consensus keys locally for each operator. Keep peer identity, validator signing and governance
keys separate. Distribute a reviewed genesis file and its cryptographic digest, public peer endpoints and a signed
release manifest. Never copy one validator signing key across simultaneously active nodes.

Definition of a created blockchain
A new chain exists when independent node processes initialize from the same reviewed genesis, agree on
committed application state, accept only valid project transactions and recover consistently from restart. A
renamed binary or a token deployed on another chain does not meet that definition for this project.

10 Devnet, validator lifecycle and upgrades
Local development topology
Run four validator containers with distinct data volumes and peer identities, one query/index service, two
app-service deployments, and three storage agents. One physical workstation is acceptable for development but
is one failure domain. Use separate machines and operators for the independence tests.

Required devnet demonstrations
Register a content manifest, accept three hosting commitments, replay the committed event stream into the
application database and show the same result after restart. Stop one validator and observe continued commits
under the test assumptions. Stop two and verify that no new commitment is presented as final. Restore nodes
without resetting the network or fabricating history.

Validator admission and removal
A council action specifies a public key, voting power, activation point and reason digest. x/authority validates the
resulting set and emits updates only at the prescribed lifecycle stage. Add tests for key rotation, removal,
duplicate keys, nonpositive total power and changed quorums. The ABCI specification governs when updates
become effective. [S06]

Upgrading without losing state
Publish a versioned migration proposal, reviewed source, release hashes and a scheduled activation point.
Rehearse on a copy of testnet state. Compare pre/post invariants and restart tests, then coordinate operator
installation. Do not assume an old binary can safely read new state after an irreversible migration.

Recovery and signing safety
Back up chain state and signer safety metadata according to the selected signer implementation. When replacing
hardware, stop and verify the old signer before activating the replacement. Keep query/public API nodes separate
from signing endpoints. A stalled network needs a documented operator recovery procedure, not an
application-level override of finality.


   Initial policy proposal: three of four council members approve ordinary network changes, with a review
   delay. Council voting is application governance, not the same process as consensus voting. A chain-wide
   stall may prevent on-chain governance itself from executing.

11 Connecting the blockchain to the app
Keep chain access behind a well-defined adapter. Python services request bounded operations through an
operator-authorized Go broadcaster or generated client. Read models come from committed events plus periodic
queries. The web client does not need to track every block.

  Client API                          POST upload-intents; GET upload status; POST publish; GET feeds; POST reports; POST
                                      removal; GET exports.

  Provider API                        Signed capability/endpoint manifest; accept offer; fetch package; return transfer receipt;
                                      report inventory.

  Chain commands                      Register provider/content, accept/renew/end lease, submit evidence and execute
                                      authorized changes.

  Chain queries                       Provider status, content manifest digest, active leases, deadlines, evidence and governance
                                      state.

  Events                              ContentRegistered, LeaseAccepted, LeaseRenewed, LeaseEnded, EvidenceAccepted,

Idempotency across systems
Use a transaction outbox in PostgreSQL for intended work. The broadcaster records attempt IDs and reconciles
unknown submissions before resending. Use a stable business ID so one successful action cannot be duplicated by
a retry with a new transaction hash. Providers enforce the same offer/lease idempotency locally.

The indexer persists a last-processed block height and event identity in the same database transaction as its
projection updates. Restart by backfilling from the checkpoint. Periodically reconcile active leases from canonical
chain queries. The database projection is a cache of coordination state, not a substitute ledger.

Multiple gateways and clear trust
Allow users and operators to configure more than one service endpoint. At beta, disclose that the chosen gateway
is trusted for read responses. Stronger clients can verify supported chain state proofs against trusted light-client
headers; comparing two unauthenticated HTTP responses is not an equivalent security guarantee.

Pending and degraded states
The UI separates requested, submitted, committed and failed operations. If the chain stops, queue requests with
explicit expiry and show them as pending. Do not activate a new storage promise based only on a local database
write. Existing approved playback may continue from reachable hosts under the last accepted terms.

STORAGE NETWORK


12 Hosting lifecycle and repair
Give every public media package a content version and a manifest listing renditions, segment hashes, byte totals
and format metadata. Store the full manifest off-chain and its digest on-chain. Nodes verify received bytes against
the manifest before advertising the package.

   OFFERED -> ACCEPTED -> ACTIVE -> RENEWED
                           |           |
                           +-> AT_RISK +-> ENDED
                           +-> EXPIRED
   Content: PENDING -> PUBLISHED -> WITHDRAWN




Provider selection
An off-chain scheduler proposes hosts using available declared capacity, compatible policies, measured
reachability and operator/failure-domain diversity. Providers must explicitly accept. The chain verifies
admissibility and accounting, not the physical truth of a declared region or independent owner. Keep a reviewed
operator registry for the beta.

Replication and publication
Transfer the package over authenticated HTTPS. Require checksum verification and provider-signed acceptance
of exact terms. Publish only after the community approves the content and the target number of active
commitments exists. Display the verification mode separately: provider acceptance, auditor attestation or a future
reviewed proof scheme.

Detect, repair and drain
An off-chain monitor tests reachability and retrieval. If a host fails, mark its local availability degraded, select a
replacement, transfer from a surviving copy and confirm a new commitment. Do not terminate the last reachable
copy before replacement. A host leaving voluntarily stops new offers, transfers accepted work and waits for
handoff or the agreed deadline.

Time, expiry and chain stalls
Use explicit real-time hosting deadlines in lease terms; do not convert block count to a guaranteed number of
seconds. Chain transitions use committed timestamps/context. Hosts apply the agreed real-time deadline locally
and show clock uncertainty. If consensus stops, on-chain expiry can lag real time; offline service extensions are
not final on-chain renewals.

Retention must be actively supported. IPFS pinning is one optional implementation mechanism, not proof of
permanent storage or guaranteed retrieval. Backups, availability and cryptographic integrity are separate
concerns. [S12]

A later cryptographic verification track
Filecoin PDP commits to stored pieces using Merkle trees, uses randomized challenges and verifies submitted
inclusion proofs on Filecoin. It is a useful reference, not a library that automatically gives a new Cosmos chain the
same properties. [S10]

Choose either an explicit external Filecoin integration with its trust/availability dependencies, or a separately
reviewed local scheme. For a local scheme, specify chunking, commitment format, challenge randomness,
deadlines, replay resistance, proof-size bounds and deterministic verification. An external randomness beacon
adds signature-verification and liveness requirements; validators must not fetch it independently during
execution.

What not to claim
Do not call a plain Merkle inclusion proof proof of a uniquely stored replica. Filecoin distinguishes Proof of
Replication from continued-storage proofs. Distinct identity, physical redundancy and low-latency retrieval
require additional arguments. [S11]

Test challenge predictability, cached proofs, outsourcing, colluding providers and selective service. Even correct
sampled proofs provide only the guarantee of their construction and threat model. Delay automatic rewards and
financial penalties until evidence rules and failure handling have independent review.


   Launch gate: I cannot confirm a secure permissionless storage-proof system from this architecture alone.
   That requires a specified construction, implementation, adversarial testing and external review.

MEDIA IMPLEMENTATION


14 Video processing and delivery
Upload and quarantine
Authorize the upload before receiving bytes. Enforce account quotas, content length, duration, dimensions and
total processing budget. Store untrusted input in quarantine under generated names; check actual file structure
rather than trusting its extension or declared MIME type. Apply layered validation and least-privilege storage
access. [S18]

Worker pipeline
A queue assigns the job to an isolated worker. Probe input, generate supported renditions and thumbnails,
normalize orientation, preserve synchronization, and attach user-provided or reviewed captions. Use CPU,
memory, disk and wall-time limits, no unnecessary outbound network, a read-only runtime and a disposable
workspace. Run as an unprivileged user.

Hash the produced segments and write a versioned manifest. Deterministic consensus does not require separate
encoders to produce byte-identical output. Instead, the chosen output is inspected and committed by digest. A
paid processing network would need a separate correctness/quality verification design; it is deferred.

Playback path
Serve an HLS master playlist and rendition playlists over HTTPS from participating hosts. Support multiple
candidate hosts, bounded retries, byte integrity checks where the client fetch path allows them, and a fallback
profile. HLS supports adaptive streaming using standard HTTP infrastructure. [S16]

Keep prefetch bounded to avoid downloading many unwatched videos. Cancel obsolete requests when the
viewer scrolls. Record startup delay, playback failures, rebuffering and bytes actually delivered, with
privacy-preserving aggregation. A successful HTTP response alone is not a completed watch.

Failure and deletion behaviour
Make jobs idempotent. A worker crash leaves a resumable or retryable job, never an apparently published video.
Use staging prefixes and an atomic publication transition. Garbage-collect abandoned uploads and failed
renditions. Removal propagates to approved hosts and indexes; independently retained copies remain outside the
operator's technical control. [S13]

Record FFmpeg build flags, included codecs and licensing obligations. FFmpeg's licence changes with optional GPL
components, and open-source licensing does not settle every codec patent issue. [S26]

APPLICATION IMPLEMENTATION


15 Identity, social records and portability
Keep login separate from chain signing
Use a reviewed authentication implementation with passkey support where practical and a secure recovery path.
A web passkey is not assumed to be a Cosmos transaction key. Keep email, recovery information and device
sessions off-chain. Operators, not normal viewers, hold the beta chain-submission credentials.

Signed, versioned social records
Use stable account IDs rather than usernames as primary keys. A proposed public-record envelope contains
schema version, author ID, record ID, sequence, previous-record digest, key ID, payload and signature. Specify
which records are public; saved videos, private preferences and raw viewing telemetry are private by default.

For JSON records, adopt a tested canonicalization profile rather than inventing one. RFC 8785 describes
repeatable JSON canonicalization for cryptographic operations and is an Informational RFC. Represent large
sequence values safely and publish cross-language test vectors. [S20]

A practical portability progression
In beta, the account host can hold a delegated signing key; disclose that custody and the need to trust the host.
Provide encrypted backups, exports and a verified migration procedure. Later, a user-controlled root identity can
delegate to replaceable hosts, subject to recovery and key-rotation tests. Changing hosts does not guarantee
every outside follower service immediately updates its records.

AT Protocol shows that independent identities, personal data servers, feeds and indexes can be separate services.
This is a reference pattern, not automatic compatibility or a feature supplied by the blockchain. [S19]

Recovery and moderation interactions
Require strong confirmation for recovery-key changes, session revocation and host migration. Preserve an
auditable authorized key history without exposing secrets. Deleting an account revokes future actions and starts
removal according to the retention policy. A user's export does not include another person's private data or
confidential moderation evidence.

Off-chain database entities
Accounts, sessions, key delegations, public records, videos, renditions, social edges, comments, moderation cases,
upload jobs, outbox entries, chain checkpoints and aggregate metrics are separate entities. Apply per-object
authorization and retention rules. Never treat a ledger inclusion as permission to access private application data.

APPLICATION IMPLEMENTATION


16 Discovery, feeds and peer assistance
Make discovery replaceable
A feed response contains stable content IDs, display metadata and candidate playback locations. Keep search and
feed indexes rebuildable from permitted records and hosting state. Expose versioned feed interfaces so another
community can offer a compatible discovery service without running the original private backend.

Start with understandable recommendations
Use candidate generation, scoring and re-ranking as a simple structure. This is a documented general
recommender pattern. [S21] Select candidates from follows, chosen topics and recent approved uploads; rank with
explicit rules; then filter blocked accounts, withdrawn videos and repeated creators.

Keep a chronological Following feed and a clear Not interested control. Treat relevance, saves, voluntary return
and negative feedback as evaluation signals. Do not optimize exclusively for watch time. Avoid publishing exact
anti-abuse thresholds that would undermine protection, while documenting the ranking factors and user controls.

Peer-to-peer is an optimization, not the only route
Add optional WebRTC segment sharing after HTTPS playback meets the agreed targets. PeerTube demonstrates a
player that combines HTTP segments from hosts/mirrors with segments from peers. [S14] Implement bandwidth
and battery limits, a visible opt-in and an immediate fallback.

Direct connections may not work through every network. TURN can relay traffic and can be self-hosted; that
relay consumes real bandwidth. [S15] Choose an origin download over a relay when it is better for reliability or
cost. Test mobile/background behaviour rather than assuming continuous sharing.

Privacy and moderation boundaries
Do not enable public IPFS advertising or browser peer sharing for private content. P2P metadata may reveal node
identity and requested content; encryption in transit is not anonymity. [S13] The client must apply current local
moderation decisions before selecting sources, including peer sources.


   Measure peer-supplied bytes separately from total payload, host traffic and relay traffic. A high peer
   percentage does not by itself prove lower total cost, better privacy or better playback.

TRUST AND SAFETY


18 Moderation, privacy and legal readiness
Moderation is an operating function
Provide clear community rules, report and block actions, an administrator queue, decisions with reasons, appeals
and an urgent escalation process. Keep sensitive case evidence access-controlled and off-chain. A signed public
label can express a community's decision without exposing the complainant.

Apply policy at account hosts, discovery services, storage admission and clients. Operators retain responsibility for
what their own services distribute. Validators do not determine the legality of every video. PeerTube offers a
precedent for local operator moderation; Apple and Google impose UGC controls for their app stores. [S31, S22, S23]

Removal must have precise promises
A removal action delists content, cancels or ends participating hosting commitments according to policy, purges
controlled caches and revokes relevant credentials. Preserve only what is legally justified under a documented
retention rule. Do not promise erasure of copies retained by independent parties, or deletion of all historical
public-ledger records. [S13]

Privacy assessment before public launch
Map the personal information each role receives, its purpose, access, retention and location. Keep raw watch
histories out of public protocols. Publish what node operators can observe. Minimize telemetry and give
meaningful controls over personalized feeds and peer contribution.

For a Canadian or Quebec operation, obtain current professional advice on applicable privacy rules, cross-border
processing, age-related requirements and incident duties. The OPC overview explains that applicability depends
on activities, organization and data flows; its cited page is dated 2018 and is not a current-law checklist. [S24]

Rights and distribution
Use original branding and a creator upload licence that covers hosting, replication, transcoding and playback.
Copyright covers software, music and audiovisual works; a hash or timestamp does not establish ownership or
permission. [S25] Defer commercial music, payments and native-store launch until their respective rights and policy
reviews are complete.


   No app-store approval, legal compliance, global deletion guarantee or safe deployment involving minors
   can be confirmed from this blueprint alone. These require operational policies and jurisdiction-specific
   review.

GOVERNANCE


19 Governance and open-source licensing
Three separate kinds of authority
Protocol governance controls validator admission, resource bounds and upgrades. Community governance
controls local membership and moderation. The project's maintainers control what code enters the reference
repository. Do not conflate any of these with ownership of users' content.

Beta governance proposal
Use four named council seats with a three-approval threshold, one approval per authorized seat, expiry and a
published delay for ordinary changes. Implement this as an auditable project module or reviewed compatible
component. Do not assume the commercially licensed Enterprise Groups module is available under the desired
terms. [S01]

Document who can pause new admissions, how keys are replaced, what happens when the council loses quorum,
and how operators choose upgrades. Emergency application actions may disable a compromised endpoint locally;
they cannot retroactively invent a committed chain decision. Publicly record material control changes.

Proposed licence split
Consider AGPLv3 for original server and application code where network-use source reciprocity is wanted, and
Apache 2.0 for original protocol client libraries where permissive reuse is preferred. AGPL's relevant source
obligation for modified network-interactive versions is in section 13; Apache has its own notice and patent terms.
Confirm compatibility for actual combinations. [S27, S28]

A protocol specification, contributed code and third-party dependencies need explicit licences. Retain original
notices and do not relicense a fork beyond the rights granted. FFmpeg build choices require their own licence
record. Source availability alone does not establish an open-source licence. [S26, S27, S28]

Community contribution system
Publish a contribution guide, code of conduct, security-reporting instructions, review rules and a decision log.
Require tests for protocol changes, migration notes for state changes and reproducible evidence for performance
claims. Assign maintainers for chain, media, application, infrastructure and trust/safety.


   The beta is a permissioned community network with open-source software. An independently governed
   permissionless network is a separate future release, not a label to apply before its controls exist.

Traffic does not vanish with peer delivery

and double-counted relay hops.

Monthly cost = fixed machines + average billable storage GB-months × storage rate + billable transfer GB ×
transfer rate + processing hours × processing rate + monitoring/backups + operational labour + trust/safety +
allocated security/legal work. Avoid double-counting resources already included in a fixed-server quote.

Collect comparable quotes in one currency, preferably CAD for planning, including transfer allowances, taxes and
overage rules. Model total network cost separately from the founder's cash outlay and from volunteer
contributions. I cannot confirm an actual monthly operating budget without traffic measurements, deployment
choices and provider quotes.

CAPACITY AND ECONOMICS


22 Transaction load and sustainable funding
Size coordination independently of video
An illustrative upload with three providers could produce one content registration and three acceptance
transactions. At 200 uploads per day this is 800 transactions/day, or about 0.0093 transactions/second on
average, before offers, renewals, audits, governance and bursts. This is a workload estimate, not chain throughput.

Audit every retained lease separately each day and the load scales with the retained catalogue. For 200
uploads/day, 90 days and three copies, there are 54,000 lease audits/day if no content leaves earlier. Batching
observations can reduce transaction count but not remove the work of checking data or retaining verifiable
evidence.

Measure proof and state costs
Record bytes and gas per transaction, peak batches, verification CPU, application-state growth, historical log
growth and catch-up time. Keep proofs, attestation batches and query responses bounded. A digest on-chain
reduces ledger bytes only if the corresponding evidence remains available where needed.

Fund storage before promising it
In beta, a community explicitly sponsors an upload allowance and lease duration. Hosts volunteer or have a
separately agreed service arrangement. Possible later revenue includes managed hosting, community
subscriptions, support and creator storage plans. These are business hypotheses, not forecasts or validated
willingness to pay.

Keep any non-cash contribution credits inside a clearly bounded service policy. Do not promise that credits are
money, an investment, or sufficient compensation for actual costs. Do not award credits simply for self-reported
storage, fabricated views or identity count.

Token decision gate
A tradable token requires its own purpose, security model, issuance, treasury controls, economic abuse analysis
and current legal/tax review. It is not necessary to create the proposed application chain. Defer it unless a
demonstrated coordination need cannot be handled more simply.


   Financial sustainability test: every accepted hosting promise has a named responsible party, a known term,
   a resource budget and a renewal or exit path. A token price is not a substitute for those commitments.
