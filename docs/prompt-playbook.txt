How to use this playbook
Use one goal at a time. These are 30 work packages, not a promise of completion after 30
messages. Corrections, reviews and blocked tests may require additional runs. No
implementation or benchmark has been executed by this prompt pack.

Prepare the repository once
Place the companion pack at the repository root. It contains AGENTS.md, docs/goals/01-...md through
30-...md, a progress tracker, a text reference and the original blueprint PDF. Merge with existing instructions
rather than blindly overwriting them. The pack contains prompts and documentation, not a working app.

Run a bounded goal
Select its model and effort in your Codex client, verify the target repository and branch, then paste the goal
or ask Codex to execute its file. Use the common instructions on page 4 as AGENTS.md. Repository
instruction files are supported by Codex [O04]. Instructions naming a model do not change the selected
model automatically.

Start dependent work from the reviewed base commit. Keep failed work on its branch, inspect the diff and
tests, then approve the merge yourself. Store the tested code revision, commands, logs and blockers in
docs/evidence/goal-NN.md. A new task must read this evidence instead of relying on chat memory.

Model and effort assignments
Suggested allocation: Astra Extra High for Goals 01-02 and 29-30; Astra High for 05-12; GPT-6.1 Sol
Medium for 03-04; GPT-6.1 Sol High for 13-28. This is a proposed engineering allocation, not a measured
optimum.

OpenAI documents Astra and GPT-6.1 Sol, and High/Extra High effort for difficult work. Availability and
controls depend on account, client and rollout [O03]. Choose the available setting explicitly and record
substitutions; do not pretend an unavailable model was used. Extra effort does not certify correctness.

Scope boundary
Target the blueprint's permissioned community beta: web application, real chain, designated hosts, HTTPS
delivery, moderation, recovery and operator tools. Native mobile apps, permissionless admission, tradable
tokens, optional P2P and advanced cryptographic storage proofs remain separate extensions [B01, pp. 3-5,
15].

REMOTE DEVELOPMENT



Codex Cloud + GitHub setup
Use GitHub for source and review; use Codex Cloud for development tasks; use an approved
integration runner for tests that exceed the workspace; deploy the eventual network to
separate operator-controlled machines. This separation is the recommended project
workflow.

Connect and prepare
In the web or desktop app, create a cloud environment, select the GitHub repository, review the prepared
setup and publish it. Codex Cloud supports coding tasks and review of changes or pull requests [O01].
Create or edit the setup before sending implementation work that needs new dependencies.

The current environment guide documents install/start configuration and isolated task workspaces. Saved
task state does not replace Git. It also lists computer/browser use as unsupported; do not assume interactive
browser tools exist. Verify headless tests separately [O02].

Use two test paths
Run permitted builds, unit tests and small integration checks inside the task. Put heavier four-validator,
media, browser and fault/load checks on a validated Linux CI/test runner when necessary. GitHub Actions
can run project test commands on hosted runners [G01]. No claim is made that the entire stack fits your
current cloud workspace.

Keep spending, external access and deployment under your control. Use only development identities.
Production validators, retained videos and the public service are not the prepared agent workspace.
ENVIRONMENT SETUP REQUEST / PART OF GOAL 04

Prepare this repository for Codex Cloud development, not production hosting. Read AGENTS.md and the
current dependency decisions. Inspect the actual environment and test Go, Python, Node, FFmpeg,
PostgreSQL, RabbitMQ, permitted local ports and any available container runtime. Do not assume Docker or
browser tools exist.
Create repeatable install/start commands and smoke checks. Use only synthetic data and freshly generated
development credentials. Keep private keys out of Git and the reusable published template. Limit network
access to approved package/documentation endpoints and development services.
Record observed capabilities in docs/environment-capabilities.md. Separate checks that run here from full
devnet, browser, failure and load tests requiring a different authorized runner. If a check cannot run, explain
the blocker and preserve its exact command; never replace it with mocked success. Ask before changing
permissions, spending money or provisioning infrastructure.
Report configuration changes and actual test results. Publishing or republishing the prepared environment is a
user action unless explicitly delegated. Recheck the branch and base commit in the next task. This setup
request belongs to Goal 04, not an additional implementation goal.
Current-versus-legacy note: follow the environment controls actually shown in your account. This guide uses OpenAI's
current Cloud environments page, not the older setup-only secrets/container-caching instructions [O02].

PERSISTENT PROJECT INSTRUCTIONS



Common contract: AGENTS.md
Copy this contract into the root AGENTS.md before running the goals. Preserve stricter
existing project instructions. Each goal relies on this contract rather than repeating it in full.

Scope and authority
Build the permissioned community beta described in docs/blueprint.md. The original PDF remains the source
for ambiguous extraction. Use a real Cosmos SDK / CometBFT application chain, not a simulated ledger.
Keep media, personal data and ordinary social interactions off-chain. No tradable token, new consensus
algorithm, proprietary-code copying, mandatory commercial cloud, or unreviewed cryptography. Treat
specifications and numeric targets as proposals until approved; never claim an audit or production readiness.

Context and changes
Before a task, read this AGENTS.md, docs/progress.md, approved decisions and only the relevant
specification sections. Verify the repository, branch and base commit; preserve unrelated work. Implement
the current goal in small reviewable changes. Do not merge, force-push, publish releases, buy services,
change access, or deploy publicly without explicit approval. Identify security-critical ambiguity and request a
decision; document reversible implementation choices without presenting them as user approval.

Cloud and credentials
Inspect the actual runtime and network permissions. Never assume Docker, browser automation, extra disk,
external peer ports or a running service exists. Do not bypass sandbox or network restrictions. Use synthetic
fixtures and fresh development-only keys; never request live validator, governance or production signing
keys. Keep secrets, key files, media uploads and database dumps out of Git, logs and shared environment
templates. Prepare reproducible external test instructions when the workspace cannot run a required check.

Implementation discipline
Pin compatible dependency versions and verify APIs against official documentation. Use typed interfaces,
explicit error handling, bounded work, object authorization and retry-safe state transitions. Chain execution
must be deterministic and free of network calls or local-clock decisions. Provider signatures are not
interchangeable with service signatures. A broadcast acknowledgement is not committed execution success.
Mocking is allowed in unit tests only; never use it as end-to-end evidence.

Verification and status
Test every change, including relevant negative cases. Never delete or weaken a requirement, skip a failing
check silently, replace an implementation with a stub, or invent logs to obtain a pass. Record the commit,
runtime, commands, exit codes, test counts and artifact locations. Distinguish IMPLEMENTED, VERIFIED,
BLOCKED and DEFERRED. A skipped or unavailable required test is not passed. Keep immutable evidence
for the tested code revision and rerun affected checks after fixes.

Handoff
Update docs/progress.md and docs/evidence/goal-NN.md. Return changed files, verified outcomes, failures,
unrun tests, residual risks and the next safe action. Maintain the requirements-to-tests matrix. End with a
proposed pull-request title and concise review summary; create the PR only when authorized. Do not
declare the whole project finished because the current goal is done.
Project commands and schemas referenced in the goals are interfaces to implement and test, not commands asserted to exist
already. Empty directories, generated stubs and mocked services are never end-to-end verification.

Review without rewriting the project
